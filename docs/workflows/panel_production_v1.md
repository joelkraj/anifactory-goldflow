# Panel composition for original manhwa production

`panel_composition_v1` is an explicit render option for a **new** `manhwa_recap_v1` / `generated_visuals_v1` production identity. It uses the compositor exercised in the Joey editing experiment, with the official narration, approved-script captions, image acceptance, render report and final-QA path. Existing identities and private editing experiments retain their contracts.

The initial option locks 1920×1080 at 30 fps, narrator-only continuous audio, generated video disabled and parallax disabled. The timeline authors its own reveals and overlaps. Incompatible options fail before preflight creates an episode. This option supports original generated artwork; external recap ingestion into production remains a separate adapter.

## Starting the next run

Wait for the operator's final script. Lock the actual channel, series, stable run slug, episode, title, exact source, selected providers and production intent through normal preflight from clean committed code. Add these options to that complete preflight command:

```text
--content-profile manhwa_recap_v1
--media-workflow generated_visuals_v1
--render-profile panel_composition_v1
--audio-target narrator_only
--generated-motion-policy disabled
--parallax-policy disabled
--run-intent production
```

Use the identity's normal narrator and image provider selection. No provider or voice switch is implied. Never retrofit these fields onto an existing run. Read `run status` before continuing and after each completed stage; use its exact next command.

## Plan artwork before generation

After approved visual beats and reference images, the panel asset stage prepares a source-bound authoring packet and draft. An editor/agent groups only beats that can be told faithfully from the same artwork. Every unique artwork order names its owner beat, covered beats, visual brief and editorial reason; every beat keeps an explicit binding. There is no reuse quota, keyword grouping, or timer-based transition cycle.

`visual panel-assets --episode-dir <episode-dir>` prepares the draft. Author it against approved story and reference context, then use `visual panel-assets --episode-dir <episode-dir> --plan <authored-candidate.json>` to validate and import it. This is editorial work for the operating agent; the user need not fill a JSON template.

Visual prompt planning authors only unique artwork orders, with their covered beats as context. The validated plan expands those orders back into the original beat IDs and timing. Reused rows do not receive provider leases or creative submissions. Materialization records the exact source asset and plan hash, zero generation cost, and separate per-beat acceptance. Missing or failed source art stops that scope; it never silently becomes a fresh paid request. Ordinary wavefront prefetch is disabled for this first profile because it can dispatch before allocation is complete.

Shared-artwork prompt packets project each covered beat to its exact narration, action/evidence, source indices, depiction, entities, local props/UI, state, population and continuity. They omit repeated parent-scene diagnostics and artifact metadata; the complete source-bound beat plan and allocation remain intact. The normal packet byte ceiling still applies and an oversized individual order stops before provider submission.

Possession is not a permanent pose. A previously received document or book can stay owned without occupying a hand in every later image. The author must prioritize the current action's hand use and the exact local narration; stale projected holding/location labels are reported as metadata discrepancies rather than forcing an impossible shot. This does not authorize disposal, a new handoff, source rewriting or automatic edits to accepted prompt prose. Confirmed errors in existing prompts still require exact reviewed repair before image spend.

For a confirmed recurring prop-staging issue before hardening, `visual review-prop-repair --episode-dir <dir> --repair-spec <request.json>` reviews explicit hash-bound artwork-owner IDs through the identity-locked planner. Its `goldflow_visual_prop_editorial_request_v1` request binds the current identity, script, beats, references/approvals, prompt plan and panel allocation, with reviewer, exact source quote and editorial direction. Three-owner packets retain the fixed 48KB limit and at most twelve workers; there is one call per packet and no automatic creative retry. Each owner receives a keep decision or exact authored span/prop-removal candidates. The command retains candidates and failures under `reports/prop_editorial/`; it does not apply changes, approve media, alter narration or submit images. Inspect the candidates before any guarded exact repair. Legitimate current prop use must be retained, and a search match alone is not a rejection.

After actual inspection, the same command accepts a `goldflow_visual_prop_editorial_acceptance_v1` spec with exact candidate paths/hashes, `actual_review: true`, reviewer/note and explicit `accept_image_ids`. Acceptance revalidates every original source and row, preserves a before snapshot and per-row authored-patch receipt, and changes only accepted owners plus their dependent aliases' creative fields. Alias timing, source excerpts and beat identity stay intact. It never creates a new provider request. Failed or unreviewed candidates are not approval; triage them without repeating successful packets.

If an import is interrupted after a source image was accepted, status can select `imagegen panel-reconcile --episode-dir <episode-dir>` to restore missing derivative panels and their ledger rows with zero provider calls. A failed source image is repaired by its exact owner ID. Changed or conflicting accepted bytes stop for triage.

Measure savings as unique scene artwork orders versus covered beats, then compare actual provider receipts. Reference images still have their own cost. Do not claim a savings percentage from the three-minute experiment, which reused artwork already generated for an earlier edit.

## Author composition after image QA

The normal motion-edit stage becomes `visual panel-plan` for this profile:

```bash
node bin/goldflow.mjs visual panel-plan --episode-dir <episode-dir> --action prepare
node bin/goldflow.mjs visual panel-plan --episode-dir <episode-dir> --action compile --recipe <authored-recipe.json>
```

Preparation writes `panel_composition_packet_<episode>.json` and `panel_composition_recipe_<episode>.json`. The packet includes exact narration excerpts, original Whisper indices, beat boundaries and accepted artwork. Inspect the artwork and author every decision. Blank or missing decisions cannot pass.

During hardening, an artwork owner's approved character-reference scope includes the exact beats covered by its validated asset order. A reaction in a later covered scene can use that scene's already approved identity without globally extending the reference plan. Unrelated scenes stay out of scope. Composition must still conceal that later reaction until its narration cue.

Layouts are `full_frame`, `inset`, `reveal`, `reaction_pair` and `page_pan`. Crop, placement, entry direction/time, overlap duration, camera path and reading holds are explicit. Main panels stay bound to their current beats. Background/context panels may carry earlier artwork forward; a later panel cannot be disclosed as context before its beat. The compiler preserves all internal beat boundaries and keeps source, caption and spoken text separate.

Compilation writes the official `panel_timeline_<episode>.json` and `panel_composition_plan_<episode>.json`, plus immutable candidate snapshots. Current script approval, narration, word timing, grouping approval, allocation, hardened prompts, accepted images, focal analysis, review decisions and per-cut ledger are hash-bound. A changed source or recipe invalidates its dependent plan. Recipe corrections recompile through the guarded stage, preserving earlier snapshots.

## Render and review

Continue through the exact `run status` render command. The panel backend supplies silent picture to the existing render path. Script-faithful captions, one continuous final audio master, final mux, upload-safe encoding and `goldflow_render_report_v2` remain authoritative.

Picture caching uses absolute frame ranges and only artwork/keys affecting each range. It preserves interpolation across chunk boundaries. Changed composition rebuilds affected chunks; narration is never cut into chunks. Private proof outputs cannot satisfy the production render stage.

Full production timelines are independent of the private workbench's 30-minute limit. The production backend validates an 80-minute timeline and renders up to four picture chunks concurrently, retaining source order before concatenation and a single continuous audio mux. Each chunk retains its own verified lossless cache. A failed chunk stops admission and preserves completed chunks for the normal reviewed render recovery.

For Fal Sunburst, use the supported early visual fork after the approved nonvisual/beat baseline. The resulting new Fal identity retains the panel contract and generates its references through the Fal adapter. Validation and bulk dispatch select only authored unique artwork owners. Finalization verifies each owner's Fal result receipt and raster, writes allocation-bound metadata, and materializes every reused panel locally with zero additional provider calls. Native per-beat image acceptance still checks all aliases; a paid owner-only completion cannot satisfy a missing or changed panel alias. The ordinary `imagegen panel-reconcile` route can restore lost derived aliases from current accepted owners.

If actual review rejects a first validation replacement, triage that exact raster before any further spend. A single later reviewed repair may use `fal/validation-recovery-second/request.json` (`goldflow_fal_second_validation_recovery_v1`), binding identity, approved script, correction, first recovery plan/review, rejected assignment/result/raster hashes and exact replacement prompt hashes. It must name every remaining rejected ID and no accepted ID, record actual review and a substantive reviewer note/reason. Status then admits `dispatch-validation-second`, original-request observation and a separate actual visual decision. Accepted first replacements and original shots remain unchanged. This is at most one additional candidate per rejected ID, counted in the ordinary retry/spend limits; any persistent rejection, transport failure or partial dispatch holds for triage. No automatic retry, provider switch or third candidate is enabled. Bulk retains the additional review hash and uses only accepted exact rasters.

After an exact reviewed Fal owner repair, reviewed-bulk finalization refreshes that owner's metadata and dependent panel copies in the new repair output directory. Only those ledger rows return to pending image QA. Prior rasters and unrelated metadata, results and QA remain unchanged. An alias-specific rejection still requires review of its allocation and finding before any paid owner regeneration; it is not an automatic repair order.

A reviewed-bulk directive may attach a missing, already approved character-state reference into a free native reference slot with `character_reference_additions` (`ref_id`, `visible_character`, `source_quote`, `reason`). It cannot displace existing references or exceed four. This requires `actual_reference_review: true`, a reviewer and substantive `reference_review_note`, and current `reference_plan_sha256`, `reference_approval_sha256`, `run_identity_sha256`, `source_script_sha256`, `beat_plan_sha256` and `panel_asset_plan_sha256`. The target must be a standalone character state approved for the exact parent scene, visibly authored in the locked shot manifest, not forbidden, and supported by a verbatim source quote within an explicitly bound beat sharing that artwork. Its actual raster must match approval. The immutable repair assignment retains the reviewed additions, directive hash, source hashes and reviewer note; the source plan, allocation and unrelated assets remain unchanged. This is an exact reviewed repair, not automatic reference discovery or global rescoping.

The prepared panel-composition packet carries the current hash-bound `image_review_decisions`, so editorial crop, readability and disclosure notes stay available to the composition author. Image acceptance alone does not approve a full-frame reveal. Inspect foreground, context and background together against the narration before compiling the authored recipe.

After preparation, `visual panel-plan --episode-dir <episode> --action author --concurrency 8` runs bounded native image-aware composition planning through the locked planning runtime. `--limit <n>` bounds new request envelopes; subsequent calls reuse exact successful envelopes, never retry failed creative outputs. Envelopes preserve parent scenes and beat order, with up to eight distinct current rasters and one earlier context raster, at most 24 current beats. These bounds package requests; they do not select layouts or transition times. Actual accepted image paths are attached to the vision planner together with narration, absolute word times, image-review notes and the allowed panel IDs. Every beat requires an explicit crop, placement, camera, layout, visible-region evidence and editorial reason. Main-image substitution, future context, missing coverage and invalid coordinates are rejected. No deterministic transition cycle, story rewrite, image generation or voice changes are enabled.

Authoring retains immutable per-envelope responses, raw calls, planner metadata, image/source/code hashes, elapsed time and reports under `reports/panel-authoring/<packet-sha256>/`. A pointer in `panel_authoring_report_<episode>.json` helps status select the next command; it is not composition approval. Successful candidates undergo the real geometry/source-order compiler in memory, but official timeline promotion still requires the separate status-reported `--action compile --recipe <candidate>`. Failed or interrupted outputs hold for exact manual reconciliation; do not delete caches or redispatch creative requests. A reviewer may construct a new packet-bound recipe from retained responses and explicit manual corrections, then compile it. Preserve the raw candidate and explain every correction. Review composed frames and actual playback before final QA; JSON validity and model region descriptions do not prove editorial quality.

If the first edited face-reference probe copies its source board instead of producing the approved single-person plate, record an actual rejection in `fal/reference-probe-review.json` (`goldflow_fal_reference_probe_review_v1`). Bind the source, identity, native reference plan, provider reference plan, rejected assignment/raster and exact unsubmitted same-identity variant IDs. Status holds all other references and directs preparation, one budgeted same-model repair, observation, and actual visual review. This appends only the single-figure output instruction and preserves the original identity input. After inspection, `review-reference-probe-repair --reviewer <name> --note <actual review>` binds the accepted raster and updates only those unsubmitted variants to use that clean identity plate. Original assignments and rasters remain archived; no submitted variant, unrelated reference, approved creative plan or provider may change. A failed repair stops for triage, and neither technical completion nor the probe decision approves the complete reference set.

Panel composition accepts the original timing identity only through that verified early Fal carryforward. It checks the immutable restart receipt, original baseline identity, unchanged nonvisual contract, approved status-snapshot hash, and exact original and copied timing bytes, and adds those dependencies to the composition provenance. An unrelated, changed or chained timing identity cannot use this route. Narration and timing are not rewritten or regenerated for the visual fork.

Review the opening with sound and sample dialogue, revelations, action, reused-art transitions and later sections. Check face crops, reading time, disclosure order, captions and synchronization. Run normal final QA after playback review. Fixture tests do not approve an episode. Packaging, upload, release and comment gates remain separate.

Foreground panels must fill their authored viewports without internal letterboxing. The native author sizes a contain viewport to the cropped artwork's aspect, or explicitly chooses cover after inspecting the safe region. The author validator checks actual source dimensions and both camera endpoints with the shared renderer geometry, allowing two pixels of rounding tolerance; it rejects padding rather than inventing a replacement crop. Camera x/y traverse available overflow (top/left zero, bottom/right one); they are not focal-point coordinates. Protect complete head silhouettes, hands/contact and relevant lettering when choosing crops.

A retained authored envelope may be reconciled after actual composed-frame review using `--action author --reviewed-overrides <absolute-json>`. The `goldflow_panel_author_reviewed_overrides_v1` directive binds the current packet, reviewer, substantive note, `actual_composed_frames_reviewed: true`, hash-bound `frame_review`, and exact `overrides` entries with `chunk_id`, `previous_chunk_path`, `previous_chunk_sha256`, substantive `reason` and complete replacement `response`. Every replacement is validated against the current packet and exact original input rasters before any new request is admitted. The adapter retains the original chunk/raw output, writes a separate manual reconciliation receipt, and makes zero replacement planner calls. New, never-requested envelopes may continue normally. Stale evidence, unknown/duplicate scopes, mismatched rasters and unreconciled old contracts remain blocked. This is not an automatic creative retry or final approval.

An authored optional `rect_to` moves or resizes the main panel inside the canvas during the same explicit `move_start_sec`/`move_end_sec` interval as its internal camera. `rect` is the initial placement; the destination must be finite and inside the canvas. Entry animation first reaches `rect`, then the authored panel movement begins. Repeated endpoint holds remain intact. This supplies panel movement separately from camera movement within the panel; no motion is inferred or added automatically. Review both endpoints and the transition for faces, text, panel overlap and fill.

A reveal entry may explicitly author `distance` (normalized canvas travel, greater than zero and at most two) and `opacity_from` (zero to one). The first key starts that distance from the settled rectangle in the chosen direction, then eases into the authored panel placement and full opacity. Omitted fields preserve the original fully offscreen, opaque entrance. These are editorial parameters, not a new automatic fade or transition cycle; preserve reading/reveal cues and review the moving result.

An explicitly requested new motion treatment of a retained, structurally valid candidate can use `visual panel-plan --episode-dir <dir> --action revise-motion --request <request.json> --concurrency 8`. This is a separate editorial dimension, not a retry of failed native crop/layout authoring. The `goldflow_panel_motion_revision_request_v1` binds `source_packet_sha256`, `recipe: {path,sha256}`, `reviewer`, the actual `operator_quote`, substantive `operator_direction`, and explicit `frozen_scene_ids` (for an already reviewed opening). Every remaining beat receives an image/narration-aware motion decision. Only panel destination, camera endpoints, move interval and refinement of an existing entrance may change; crops, initial placement, layouts, contexts, images, source text and reveal cues remain fixed. A static result needs its own narrative reason. There is no deterministic motion cycle or target percentage.

Register that exact request as `panel_motion_revision_request_<episode>.json` before running status. Status then selects motion revision, a candidate compile, or exact manual reconciliation as appropriate. Motion candidates retain the locked native planner's actual raster inputs, responses, metadata, exact source/code hashes and per-envelope reports under `reports/panel-motion-revisions/`. Each base recipe permits one bound revision request. Successful results are reused; failed/interrupted envelopes or changed request/code hold for manual reconciliation, never redispatch. Neither an all-green report nor a new recipe promotes the official timeline. Review the actual movement, then use the ordinary guarded compile and render paths. The revision does not change narration or repair a reported voice defect.
